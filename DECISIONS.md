# FlowForge — Spec Deviations

Every place the build diverged from PHASE2.md, one line each: what changed, why, when. Append, don't rewrite.

- **cron-parser v5, not v4** — M1 approved `cron-parser` as a dependency for cron validation in `job-config.schema.ts`. The version tentatively picked (v4.9.0) is marked deprecated upstream ("no longer maintained, upgrade to v5"), so v5 was used instead — same library, current major. 2026-08-11.
- **Hosted Neon + Upstash, not local Docker, as the default in SETUP.md** — §13 asked which the owner would prefer at M1. Neither Docker nor a local Postgres/Redis is installed on the build machine, so hosted free tiers became the default path in `SETUP.md`. `docker-compose.yml` still ships in the repo as an approved optional alternative. 2026-08-11.
- **stripe-webhook-reconcile seeded at 90% success (not mockData's 96.1%)** — §5's health rule looks only at a job's last-20 runs. At mockData's original 96.1% and stripe's high daily volume (~100-150/day), that 20-run sample was a coin flip between reading `healthy` and `degraded` — verified by direct simulation. 90% reliably lands the derived health at `degraded` (the "mildly degraded" story the owner asked for) without changing the job's other config. 2026-08-11.
- **`/api/failures/clusters` built for real at M3, not deferred to M10** — §14 formally assigns "code-side clustering, `/api/failures/clusters`" to M10, but it's a GET endpoint in §6's read-API contract with zero AI dependency (§9.4 step 2 already says clustering happens in code, not via the model). Owner approved building it now rather than stubbing then rebuilding; M10 will only add `/api/ai/diagnose` on top of the clustering that already exists. 2026-08-11.
- **churn-model-retrain's seeded `timeoutMs` reduced from 1,800,000ms to 900,000ms** — the seed's own pre-insert validation against `jobConfigSchema` (§7.1's 1000–900000 bound) correctly caught that the original 30-minute value exceeded the 15-minute ceiling and refused to seed. Fixed the seed data, not the schema bound, per owner's explicit instruction. Its simulated run duration was reduced in step from ~22m03s (mockData's original average) to 840,000ms (14 min) so it stays comfortably under the new timeout while remaining the slowest job in the fleet by a wide margin (next slowest, postgres-nightly-backup, runs ~3m41s). 2026-08-11.
- **Fixed a Date-bind bug in `activityBucketsSince`** — a raw JS `Date` was interpolated directly into a raw `sql` template as a bind parameter (`${since}`), which the `postgres` driver rejects outside Drizzle's typed query-builder context (`TypeError: The "string" argument must be of type string... Received an instance of Date`). Fixed by serializing to `.toISOString()` before interpolation. Grepped every repository for the same pattern — it was the only raw `sql` template in the codebase binding a non-column value; everywhere else a `Date` is used, it goes through typed helpers (`gte`, `gt`) which serialize correctly. 2026-08-11.
- **Failure clustering was seeing only 2 distinct `(error_type, message)` combinations — a seed bug, not a clustering bug** — each of the six seeded jobs had exactly one fixed `taskInput.failureMode`, so `error_type` never varied within a job's dead-lettered runs, and `runs.error_message` was hardcoded to the literal string `"dead-lettered after N attempts"` for every dead-lettered run regardless of job, discarding the real per-mode failure detail that already existed for the log lines. Fixed by: (1) adding an optional `secondaryFailureMode`/`secondaryFailureModeShare` to `SeedJobDef`, mixing `timeout` into docs-embedding-index (35%) and stripe-webhook-reconcile (20%) alongside their primary modes, matching §9.4's own example of rate-limit + timeout clustering; (2) writing the real per-mode message (already generated for logs via `failureMessage()` in `seed-logs.ts`, now exported) onto `runs.error_message` instead of the generic constant. Clusters went from 2 to 4 across the 30-day window. 2026-08-11.
- **Added `pnpm db:touch-workers` (server/src/db/seed/touch-workers.ts), outside the M0–M11 milestone list** — no live worker process exists until M5, so seeded "online" heartbeats are static and inevitably cross §5's 15-second offline threshold as soon as real time passes between seeding and viewing — this isn't fixable by picking a different seed value, since the same drift happens regardless. This script re-writes `lastHeartbeatAt` to "now" for the 7 workers meant to read online, leaving worker-08 stale, without re-seeding everything else. Documented in `SETUP.md` as a step to run before demoing/viewing. Needed only until M5 brings a real heartbeat loop, at which point this script should be deleted. 2026-08-11.
- **`successRatePct` on `/api/stats/overview` now excludes `skipped_duplicate` from its denominator (and, for consistency, matches the same "counted" definition already used by job-level health)** — a correctly deduplicated run is neither a success nor a failure and shouldn't move a success rate in either direction. The Overview query previously used `count(*)` (every status) as the denominator while `job.service.ts`'s per-job health/success-rate already excluded `skipped_duplicate` — two different definitions of "counted" for the same underlying concept. Fixed by lifting `job.service.ts`'s private status sets into `config/constants.ts` (`SUCCESS_RATE_COUNTED_STATUSES`/`SUCCESS_RATE_SUCCESS_STATUSES`) as the single shared definition, imported by both. `runsLast24h` still reports a true unfiltered count — it's a volume metric, not a success-rate input. 2026-08-11.
- **stripe-webhook-reconcile's flat 90% baseline (from the 2026-08-11 M2 entry above) replaced with a structural degradation ramp** — a flat failure rate leaves whether the job's trailing-20-run health sample lands `healthy` or `degraded` to RNG luck on that specific 20-run streak; this was observed in practice after a reseed shifted the RNG sequence and the tail happened to land on 20/20 successes, flipping the job to `healthy`. Replaced with a ramp (same shape family as docs-embedding-index's, shallower peak: ~14% recent failure rate vs. a ~10% flat baseline) that structurally weights the most-recent days toward the "degraded" band, so the outcome no longer depends on which exact runs land in any given trailing-20 sample. Verified by a new end-of-seed assertion (see below) across two consecutive seed runs. 2026-08-11.
- **Added an end-of-seed health assertion** — each `SeedJobDef` now carries an `intendedHealth` field; after every job is inserted, the seed computes its actual health via the same `deriveJobHealth` rule from `job.service.ts` and compares. If any of the six jobs doesn't match its intended health, the seed logs every job's intended-vs-actual value, then exits non-zero — loudly, after the data is already committed (not inside the transaction, so a mismatch is visible and debuggable rather than silently rolled back). Confirmed passing on two consecutive runs. 2026-08-11.
- **Fixed the error-fingerprint normaliser to strip trailing retry/dead-letter framing before fingerprinting, not just numbers/IDs/timestamps** — two messages describing the identical underlying fault (`"upstream 429 Too Many Requests · attempt 1/3"` vs. `"upstream 429 Too Many Requests · attempt 3/3 · dead-lettered after 3 attempts"`) were fingerprinting to different keys because the trailing clause describing retry position varies by definition, not because the numbers inside it weren't stripped. `fingerprintErrorMessage` now strips `"· attempt N/M"` and `"· dead-lettered after N attempts"` clauses before the digit-stripping pass, so the same fault clusters together regardless of where in the retry cycle it was caught. This is a normaliser fix, not a seed fix — the same shape of message will occur with real production errors once M5's real workers exist. 2026-08-11.
- **Workers page's replica +/− buttons are now disabled with a tooltip, not removed or left fake** — the mock UI let them increment/decrement a local `replicas` counter with no backing API; job/worker write endpoints (including any scale action) don't arrive until M7. Kept the same visual layout as `docs/screenshots/workers.png` (buttons, count, drain-time slot repurposed as a note) rather than dropping the control, so the page doesn't silently pretend scaling works. Owner's explicit call when this was flagged as a forced visual/behavioral change. 2026-08-11.
- **Frontend displays `job.id` (the slug) everywhere the screenshots show a job name, not `job.name` (the human title seeded at M2)** — `JobSummary` carries both: `id` is the kebab-case slug (`competitor-pricing-scrape`), `name` is a title-cased label ("Competitor Pricing Scrape") seeded for possible future display use. Every M0-era screenshot shows the monospace slug as the job's on-screen identity, matching an ops-dashboard convention (it's what appears in logs/configs). Owner's explicit call when this was flagged as a forced choice between the two fields. `job.name` stays in the API, unused by the UI for now. 2026-08-11.
- **M5's `simulate.task.ts` supports `failureMode`/`failureRate` and can genuinely fail, even though M5 has no retry loop** — §14 groups "Retries with exponential backoff, dead-lettering" into M6, which read as failure-mode support belonging there too. Owner explicitly pulled failure-mode support forward: a task that can only succeed isn't a real test of the execution path, and M6 then adds retries on top of a handler already proven to fail correctly. A failed M5 run lands in `failed` status with no further attempts — no retry, no dead-letter — those remain M6. 2026-08-11.
- **Drizzle table definitions (`jobs`, `runs`, `run_logs`, `workers`, `idempotency_records`, `ai_cache`) moved from `server/src/db/schema/` into `packages/shared/src/db/schema/`** — the worker writes to these tables directly (server and worker are peers sharing one database, not client and server to each other), so both processes need the exact same column definitions. Two hand-maintained copies would drift the first time either changed — the same reasoning §12.3 already applies to shared types/enums, extended to schema. `server/src/db/schema/index.ts` is now a one-line re-export of `@flowforge/shared` so every existing import path (`from '../db/schema/index.ts'`) keeps working unchanged. Migrations and `drizzle.config.ts` stay in `server/` — one package still owns migration generation. `packages/shared` gained `drizzle-orm` as a dependency. §3's target tree in `phase2.md` updated to reflect the new location. 2026-08-11.
- **BullMQ queue name (`flowforge:jobs`) and job payload shape (`{runId, jobId}`) moved to `packages/shared/src/constants/queue.ts`** — same reasoning as the schema move: anything that crosses the wire between the server (enqueues) and the worker (dequeues) belongs in shared, not duplicated as a hand-matched string constant and interface in each package. 2026-08-11.
- **M5 pulls a minimal slice of §7.3.4 (worker heartbeat/registration) forward from M6** — `runs.worker_id` has a foreign-key constraint against `workers.id`, so a real worker process executing a real run needs a `workers` row to reference or the write fails. Rather than leave `worker_id` null for the whole of M5 (which would leave the Overview's "busiest workers" and the recent-runs table unable to show which worker did the work), the worker now upserts its own `workers` row on boot (`worker/src/registration.ts`) and marks itself `offline` on graceful shutdown. Scoped deliberately tight: no heartbeat loop, no stale-heartbeat detection, no `draining` state — all of §7.3.4's remaining behaviour stays in M6. 2026-08-11.
- **`POST /api/jobs/:id/trigger` returns 409 `JOB_PAUSED` for a paused job rather than enqueuing anyway** — a paused job means "don't run this"; a manual trigger against it is either a mistake or a stale UI. The owner resumes the job first if a one-off run on a paused job is genuinely wanted. 2026-08-11.
- **`deriveJobHealth` (the §5 health rule) moved from `server/src/services/job.service.ts` to `packages/shared/src/rules/job-health.rule.ts`, along with its thresholds and status sets** — M6 needs the worker to recompute a job's health after every run it finishes, and the worker can't import from `server/` (sibling packages, no dependency relationship). Calling back into the server's HTTP API to trigger recomputation was rejected — it's the same "worker calls server over HTTP for something server and worker should just share" pattern already rejected for logging at M5. `deriveJobHealth` is a pure function over a status array with no DB/HTTP dependency, so it has no reason to live in a server-only package. `job.service.ts` (read API), the seed script, and the worker now all import the one implementation. Its test file moved alongside it (`job-health.rule.test.ts`), expanded to cover all four health states plus the skipped-duplicate/non-terminal-status exclusions and the 20-run sample-size cap. 2026-08-11.
- **M6: real retries with exponential backoff, dead-lettering, worker-side idempotency, heartbeat/draining/graceful shutdown, and consecutive-failure alerting.** Key implementation notes: (1) BullMQ's `job.attemptsMade` is only incremented *after* the processor returns/throws, so `currentAttempt = attemptsMade + 1` inside the processor — verified against BullMQ's own source (`job.js`/`backoffs.js`), not assumed. (2) The retry-delay log line (`"attempt N/M failed, retrying in Xs"`) computes its delay with the exact formula BullMQ's exponential strategy uses (`Math.round(2^(attempt-1) * baseMs)`), so what the log says matches what actually happens. (3) The idempotency guard runs worker-side, once, only on attempt 1 of a run — a run already mid-retry already holds its claim from attempt 1. (4) A dead-lettered run still gets rethrown to BullMQ after the run row is updated, so BullMQ's own bookkeeping (its failed set, `attemptsMade`) stays consistent; the run row remains the single source of truth the API reads from. (5) Consecutive-failure alerting is a direct in-process call (no queue, no `runs` row of its own) — an alert is infrastructure reacting to a job's state, not a job the user scheduled, and giving it its own run row would pollute run history/success rates/failure clusters with something nobody triggered. It writes an `error` line into the *triggering* run's own `run_logs` so Job Detail shows an alert fired and where it went, and never fails the run or crashes the worker if delivery fails (caught and logged only). 2026-08-11.
- **Worker rows accumulate on every boot with no `WORKER_ID` set — acceptable for Phase 2's local dev loop, but Phase 3 needs a reaping story.** Confirmed by a real cleanup this session: 20 stray `worker-<8hexchars>` rows (from before sequential `worker-NN` ids existed) plus one `"[object Promise]"` row (a transient `tsx watch` hot-reload artifact caught mid-edit — audited every write path to `workers.id`, confirmed only one call site, correctly typed and awaited, so not a live bug) had accumulated in the dev database. Cleaned up by nulling `runs.worker_id` on the 8 run rows that referenced a stray worker (preserving run history) before deleting the 20 stray worker rows. Phase 2 doesn't need automatic reaping — restarting a dev worker without `WORKER_ID` is rare enough to clean up by hand — but Phase 3, running long-lived, will need something (e.g. reap workers offline for >N days) that isn't built now. 2026-08-11.
- **SIGTERM could not be verified end-to-end on this Windows dev machine — SIGINT was verified instead, real gap flagged for Phase 3.** Windows doesn't reliably deliver SIGTERM to an external Node process: `taskkill` (non-forceful) errored outright, and `process.kill(pid, 'SIGTERM')` from a separate process reached nothing (the target process's handler never fired, task ran to natural completion both times) — a Windows platform limitation, not a bug in `shutdown.ts`, since the identical handler is registered for both signals and the code path is signal-agnostic. SIGINT (Ctrl+C, delivered interactively by the owner in a foreground terminal) IS reliably deliverable on Windows and exercises the exact same `shutdown()` function — verified end-to-end: `draining` status set immediately, `worker.close()` correctly raced against the grace-period timeout (confirmed both the "drained cleanly" path with no in-flight work, and the "hit its shutdown grace period — exiting anyway" path with a 221s task that couldn't finish inside the 30s window), heartbeat stopped, `markWorkerOffline()` ran, process exited. Phase 3 deploys to Linux containers, where the container runtime sends real SIGTERM on stop/restart — that path needs re-verification there, since it was never actually exercised here, only assumed equivalent to the (verified) SIGINT path. 2026-08-11.
- **Found and fixed a real idempotency-guard bug during the stalled-job-recovery test: a worker dying mid-task permanently poisoned that run's idempotency key for its full TTL, so recovery could never actually happen.** Reproduced live, not hypothetically: `worker-21` was SIGINT'd mid-task (221s job, 30s grace period — genuinely couldn't finish in time), died with the run still `running`. BullMQ's own stalled-job detection correctly noticed and handed the job to a fresh `worker-22` — but `tryClaimIdempotencyKey`'s original logic (`setWhere: expires_at < now`) treated the still-unexpired `idempotency_records` row from the dead attempt as held by someone else, so the recovery attempt was wrongly marked `skipped_duplicate` and abandoned; the run stayed stuck at attempt 1/3 forever, never retried, never dead-lettered. Root cause: the guard's job is to stop a *different* run from claiming an in-use key (two overlapping cron fires), but it was blocking the *same* run reclaiming its own key just as hard — exactly the case BullMQ-driven recovery produces on every worker crash. Fixed by adding a same-`run_id` fast-path to the `ON CONFLICT` clause (`setWhere: runId = $runId OR expires_at < now`), so a run reclaiming its own still-valid key always wins, while a genuinely different run still correctly loses. Added a regression test (`idempotency.repository.test.ts`: "wins a second claim by the SAME run even while its key is still unexpired") alongside the existing "loses to a different unexpired run" test, so the fix can't silently regress into permissiveness. The stuck run (`1207f8f5-…`) was recovered with a one-off script (`server/scripts/recover-stuck-run.ts`, deleted after use — reset the row to `queued`, re-enqueued fresh) and re-verified end-to-end: the new attempt correctly reclaimed the same key and proceeded to execute instead of skipping. `server/scripts/verify-duplicate-skip.ts` and `check-bullmq-job-state.ts` are kept as reusable reproduction/debug tools for M7 and M10. 2026-08-11.
- **M7: scheduling built on BullMQ's Job Scheduler API, not the older repeatable-jobs API.** `upsertJobScheduler(jobSchedulerId, repeatOpts, jobTemplate)` / `removeJobScheduler(id)` (BullMQ 5.81.3) are the non-deprecated path (the older `queue.add({repeat})`/`removeRepeatableByKey` are marked for removal in BullMQ v6) and are keyed by an id the caller controls — used the job's own slug, so add/update/remove are precise single-call operations rather than needing to reconstruct a composite repeat key. §7.4's wording ("repeatable jobs") describes the behaviour, not a mandate for that specific legacy API name. 2026-08-11.
- **The schedule-tick consumer lives in `server/`, not `worker/` — a second, server-only BullMQ queue (`flowforge-schedule-ticks`), never touched by the worker package.** BullMQ's Job Scheduler fires a job on each cron slot, but that job can only carry a static payload (`{jobId}`) — it can't carry a pre-created `runId`, since that run doesn't exist until the slot actually fires. Something has to sit between "the schedule fired" and "a real run exists to hand to the worker," and that something is exactly what `enqueue.service.ts`'s manual-trigger path already does (insert a queued run row, enqueue it onto the real job queue) — so `schedule-tick.service.ts` reuses that same `enqueueRun` function, with `triggerSource` and `scheduledAt` as the only differences from a manual trigger. Kept out of `worker/` for two reasons: creating a run row and enqueueing is a database+queue operation, not task execution, so it belongs with the server by the same layering `worker/` already follows everywhere else; and every worker replica consuming the tick queue would fire each cron slot once *per replica* rather than once total, which is a real failure mode, not just a layering preference — Phase 3's horizontally-scaled workers depend on this staying server-only. 2026-08-11.
- **`scheduled_at` for a scheduled run is recovered from the BullMQ scheduler job's own id (`repeat:<schedulerId>:<slotTimestampMs>`), not from `job.timestamp` or `Date.now()` at tick-processing time.** `job.timestamp` is when BullMQ *created* the job (enqueue time), not the cron slot it represents — using it would make the idempotency key (which templates in `{{scheduled_at}}`) drift under load, since two ticks racing to be processed would get different timestamps for what should be the same logical slot. The scheduler job's id format is BullMQ's own documented convention for recovering the exact slot; `slotTimeFromSchedulerJobId` parses it with a regex and falls back to the passed-in `firedAt` only if the id doesn't match the expected shape (defensive, not expected to trigger in practice). 2026-08-11.
- **Reconciliation is a targeted single-job upsert/removal on every job mutation (create/update/pause/resume/delete), with a full diff-and-fix pass reserved for server boot and a standalone script.** `reconcileJob` always calls `removeJobScheduler` then, only if the job should still be scheduled, `upsertJobScheduler` again — remove-then-upsert unconditionally, not diff-first, since correctness matters more than saving a couple of Redis round-trips on a low-volume mutation path. `reconcileAllSchedules` does the equivalent full pass (every active-cron-undeleted job gets a scheduler, every scheduler with no matching job gets removed) and runs once at server boot to catch drift from a crash or a manual DB edit between runs. `server/scripts/reconcile-schedules.ts` runs the same full pass on demand, without a restart — kept permanently as both a manual-fix tool and the way to verify reconciliation is actually working. 2026-08-11.
- **DELETE /api/jobs/:id soft-deletes via a nullable `deleted_at timestamptz` column, not a new `status` enum value and not a hard row delete.** `runs.job_id` has a foreign-key to `jobs`, and by M7 thousands of run rows reference real job rows — hard-deleting would either cascade away run history or fail on the constraint. `status` deliberately stays exactly `active`/`paused` as §5 defines it, so `deriveJobHealth`'s `paused` branch and every other place that branches on `status` needed zero changes; `deleted_at IS NOT NULL` is purely a listing/lookup exclusion filter, applied in `findAllJobs`/`findJobById` (and therefore everywhere that reads through them — the API's list/detail routes, and `job.service.ts`'s per-job aggregation). Existing queued/running runs are left alone to finish naturally on delete — the job row is a tombstone, not gone, so a worker mid-run can still read its task config; no 409 is raised for in-flight work. `stats.repository.ts`'s own aggregates query `runs`/`workers` directly, not `jobs`, so a deleted job's historical runs still correctly count toward global 24h stats — deletion removes a job from *listing*, not from history. 2026-08-11.
- **PATCH /api/jobs/:id is a true deep partial, hand-built rather than zod's `.partial()`.** Zod v4 refuses `.partial()` on any schema carrying a `.superRefine()` (partial-ing the shape could invalidate the refinement's own assumptions) — `jobConfigSchema`'s `trigger` sub-schema has exactly that (the cron-requires-a-valid-expr check), so `triggerSchema` was split into a bare `triggerShape` (exported, no refinement) that `updateJobRequestSchema` partials, while `triggerSchema` (shape + refinement) stays what create/full-validation use. `updateJobRequestSchema` itself is `.strict()` (unknown keys rejected) and excludes `name` (a job's id/slug isn't something PATCH changes). The safety net that matters most: PATCH's partial schema intentionally skips the cron refinement, but `job.service.ts`'s `updateJob` deep-merges the patch onto the job's *current full config* and re-validates the *entire merged result* against full `jobConfigSchema` (refinement included) before saving — so a patch that would produce an invalid whole (e.g. flips `trigger.type` to `cron` without ever supplying `expr`) is still caught, just at the merge-and-revalidate step rather than at the request-parsing step. No other guardrails on what PATCH can change (task type, cron, retry policy are all legitimate edits) — a job's identity is its id, not its config, and each run already snapshots what it needs (`max_attempts`, etc.) at enqueue time, so a later config change doesn't retroactively affect run history. 2026-08-11.
- **The server is a scheduling singleton — running more than one server instance would fire every cron slot once per instance.** Both the boot-time `reconcileAllSchedules()` call and the in-process `scheduleTickQueue` consumer (`schedule-tick.worker.ts`) assume exactly one server process is registering schedulers and consuming ticks. This is fine for Phase 2 (one server process, one deploy target) but is a real constraint for Phase 3: horizontally scaling the server (not just the worker) would need either a single elected scheduler-owner or moving schedule-tick consumption to something that's inherently single-instance regardless of server replica count. Not built now — noted so Phase 3 doesn't get designed into a corner assuming the server is already safe to scale. 2026-08-11.
- **M7 done-when criteria verified live, not just via unit tests.** Created a real job (`m7-every-minute-test`, `* * * * *`, via `POST /api/jobs`) against the live Neon+Upstash stack with a real worker running. Observed three consecutive unattended firings exactly on the minute boundary (10:09:00Z, 10:10:00Z, 10:11:00Z), each `triggerSource: schedule`, each `succeeded`, with nobody touching anything between them. Paused at 10:11:33Z (before the 10:12:00Z slot) and confirmed via a 90-second wait that no run appeared at 10:12 or after — pause stopped the schedule within one cycle. Resumed at 10:13:28Z and confirmed a fresh run fired at the very next slot, 10:14:00Z. Then verified DELETE: 204 on delete, immediate 404 on a follow-up GET (soft-deleted, excluded from lookups) — confirming the tombstone behaviour end-to-end, not just by reading the code. 2026-08-11.
- **M8: live updates bridge worker↔server via Redis pub/sub (`flowforge:events`), not an in-process-only event bus.** §8 describes "an in-process event bus" that queue events and worker updates publish to — but the worker is a separate OS process from the server with no existing channel back to it (confirmed: no HTTP callback, no existing pub/sub, direct-DB-writes-only architecture since M5/M6). An in-process `EventEmitter` alone can only see server-originated events (`run.queued`, published directly in `enqueue.service.ts`). Every worker-originated event — `run.started`/`run.finished` (worker.ts), `run.log` (task-logger.ts, one publish per log line), `worker.updated` (heartbeat.ts every 5s, plus shutdown.ts's `draining` and registration.ts's online/offline) — publishes fire-and-forget onto a Redis channel (`packages/shared/src/constants/realtime.ts`); the server's `realtime/redis-subscriber.ts` subscribes and re-emits onto `realtime/event-bus.ts`, which `realtime/sse.handler.ts` fans out to connected clients. Both processes already hold a Redis connection (BullMQ), so this adds no new infrastructure. Owner's explicit choice over BullMQ `QueueEvents` + a DB poll, given it covers every event type uniformly (`run.log` has no BullMQ job-state equivalent) and needs no separate poll loop. A publish failure is caught and logged, never thrown — a live-update notification must never fail or slow down a run (owner's explicit instruction). 2026-08-11.
- **M8: `stats.tick` broadcasts the full `/api/stats/overview` payload every 3s, not a lighter delta.** `realtime/stats-tick.ts` calls the exact same `getStatsOverview()` the GET endpoint uses. Owner's explicit call: one source of truth, no risk of the tick and the endpoint disagreeing about what "queue depth" or "success rate" mean; revisit only if volume ever makes recomputing the full aggregate every 3s expensive (not the case at current seed/demo data volumes). 2026-08-11.
- **M8: SSE fully replaces polling on the frontend — `useRunLogs.ts` (4s log poll) deleted, not kept as a fallback.** Owner's explicit instruction: "no polling" is M8's stated done-condition, and a fallback poll would quietly defeat it while also giving the app two data paths that could disagree. Instead, `useLiveStream.ts` reconnects with exponential backoff (1s→15s cap) on a dropped connection and exposes a `reconnectedAt` timestamp; `App.tsx` uses it to refetch every resource once on reconnect (stats, jobs, workers, failures, and the open job's detail/runs if one is open), closing any gap in the stream without re-establishing a poll loop. Run-log history for a newly-opened run is still fetched once via `GET /api/runs/:id/logs` (SSE only carries lines written after the tab connects, not history) — this is a one-shot load on run-switch, not an interval. 2026-08-11.
- **M8: the Overview counter-animation (§11's "keep the animation, feed it real numbers") stays first-load-only under a continuous 3s tick stream.** The existing `hasAnimatedRef` guard in `App.tsx` already only ran the ease-in animation once and set counters directly on every later update — that behavior was correct for the one-shot fetch and needed no new guard for `stats.tick`; it was only repointed from `stats.data` to `overviewStats` (`liveStats ?? stats.data`, i.e. the latest tick once one has arrived, falling back to the one-shot fetch before the first tick lands).
