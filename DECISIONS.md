# FlowForge — Spec Deviations

Every place the build diverged from PHASE2.md, one line each: what changed, why, when. Append, don't rewrite.

- **cron-parser v5, not v4** — M1 approved `cron-parser` as a dependency for cron validation in `job-config.schema.ts`. The version tentatively picked (v4.9.0) is marked deprecated upstream ("no longer maintained, upgrade to v5"), so v5 was used instead — same library, current major. 2026-08-11.
- **Hosted Neon + Upstash, not local Docker, as the default in SETUP.md** — §13 asked which the owner would prefer at M1. Neither Docker nor a local Postgres/Redis is installed on the build machine, so hosted free tiers became the default path in `SETUP.md`. `docker-compose.yml` still ships in the repo as an approved optional alternative. 2026-08-11.
- **stripe-webhook-reconcile seeded at 90% success (not mockData's 96.1%)** — §5's health rule looks only at a job's last-20 runs. At mockData's original 96.1% and stripe's high daily volume (~100-150/day), that 20-run sample was a coin flip between reading `healthy` and `degraded` — verified by direct simulation. 90% reliably lands the derived health at `degraded` (the "mildly degraded" story the owner asked for) without changing the job's other config. 2026-08-11.
- **`/api/failures/clusters` built for real at M3, not deferred to M10** — §14 formally assigns "code-side clustering, `/api/failures/clusters`" to M10, but it's a GET endpoint in §6's read-API contract with zero AI dependency (§9.4 step 2 already says clustering happens in code, not via the model). Owner approved building it now rather than stubbing then rebuilding; M10 will only add `/api/ai/diagnose` on top of the clustering that already exists. 2026-08-11.
- **churn-model-retrain's seeded `timeoutMs` reduced from 1,800,000ms to 900,000ms** — the seed's own pre-insert validation against `jobConfigSchema` (§7.1's 1000–900000 bound) correctly caught that the original 30-minute value exceeded the 15-minute ceiling and refused to seed. Fixed the seed data, not the schema bound, per owner's explicit instruction. Its simulated run duration was reduced in step from ~22m03s (mockData's original average) to 840,000ms (14 min) so it stays comfortably under the new timeout while remaining the slowest job in the fleet by a wide margin (next slowest, postgres-nightly-backup, runs ~3m41s). 2026-08-11.
- **Fixed a Date-bind bug in `activityBucketsSince`** — a raw JS `Date` was interpolated directly into a raw `sql` template as a bind parameter (`${since}`), which the `postgres` driver rejects outside Drizzle's typed query-builder context (`TypeError: The "string" argument must be of type string... Received an instance of Date`). Fixed by serializing to `.toISOString()` before interpolation. Grepped every repository for the same pattern — it was the only raw `sql` template in the codebase binding a non-column value; everywhere else a `Date` is used, it goes through typed helpers (`gte`, `gt`) which serialize correctly. 2026-08-11.
- **Failure clustering was seeing only 2 distinct `(error_type, message)` combinations — a seed bug, not a clustering bug** — each of the six seeded jobs had exactly one fixed `taskInput.failureMode`, so `error_type` never varied within a job's dead-lettered runs, and `runs.error_message` was hardcoded to the literal string `"dead-lettered after N attempts"` for every dead-lettered run regardless of job, discarding the real per-mode failure detail that already existed for the log lines. Fixed by: (1) adding an optional `secondaryFailureMode`/`secondaryFailureModeShare` to `SeedJobDef`, mixing `timeout` into docs-embedding-index (35%) and stripe-webhook-reconcile (20%) alongside their primary modes, matching §9.4's own example of rate-limit + timeout clustering; (2) writing the real per-mode message (already generated for logs via `failureMessage()` in `seed-logs.ts`, now exported) onto `runs.error_message` instead of the generic constant. Clusters went from 2 to 4 across the 30-day window. 2026-08-11.
- **Added `pnpm db:touch-workers` (server/src/db/seed/touch-workers.ts), outside the M0–M11 milestone list** — no live worker process exists until M5, so seeded "online" heartbeats are static and inevitably cross §5's 15-second offline threshold as soon as real time passes between seeding and viewing — this isn't fixable by picking a different seed value, since the same drift happens regardless. This script re-writes `lastHeartbeatAt` to "now" for the 7 workers meant to read online, leaving worker-08 stale, without re-seeding everything else. Documented in `SETUP.md` as a step to run before demoing/viewing. Needed only until M5 brings a real heartbeat loop, at which point this script should be deleted. 2026-08-11.
- **`successRatePct` on `/api/stats/overview` now excludes `skipped_duplicate` from its denominator (and, for consistency, matches the same "counted" definition already used by job-level health)** — a correctly deduplicated run is neither a success nor a failure and shouldn't move a success rate in either direction. The Overview query previously used `count(*)` (every status) as the denominator while `job.service.ts`'s per-job health/success-rate already excluded `skipped_duplicate` — two different definitions of "counted" for the same underlying concept. Fixed by lifting `job.service.ts`'s private status sets into `config/constants.ts` (`SUCCESS_RATE_COUNTED_STATUSES`/`SUCCESS_RATE_SUCCESS_STATUSES`) as the single shared definition, imported by both. `runsLast24h` still reports a true unfiltered count — it's a volume metric, not a success-rate input. 2026-08-11.
- **stripe-webhook-reconcile's flat 90% baseline (from the 2026-08-11 M2 entry above) replaced with a structural degradation ramp** — a flat failure rate leaves whether the job's trailing-20-run health sample lands `healthy` or `degraded` to RNG luck on that specific 20-run streak; this was observed in practice after a reseed shifted the RNG sequence and the tail happened to land on 20/20 successes, flipping the job to `healthy`. Replaced with a ramp (same shape family as docs-embedding-index's, shallower peak: ~14% recent failure rate vs. a ~10% flat baseline) that structurally weights the most-recent days toward the "degraded" band, so the outcome no longer depends on which exact runs land in any given trailing-20 sample. Verified by a new end-of-seed assertion (see below) across two consecutive seed runs. 2026-08-11.
- **Added an end-of-seed health assertion** — each `SeedJobDef` now carries an `intendedHealth` field; after every job is inserted, the seed computes its actual health via the same `deriveJobHealth` rule from `job.service.ts` and compares. If any of the six jobs doesn't match its intended health, the seed logs every job's intended-vs-actual value, then exits non-zero — loudly, after the data is already committed (not inside the transaction, so a mismatch is visible and debuggable rather than silently rolled back). Confirmed passing on two consecutive runs. 2026-08-11.
- **Fixed the error-fingerprint normaliser to strip trailing retry/dead-letter framing before fingerprinting, not just numbers/IDs/timestamps** — two messages describing the identical underlying fault (`"upstream 429 Too Many Requests · attempt 1/3"` vs. `"upstream 429 Too Many Requests · attempt 3/3 · dead-lettered after 3 attempts"`) were fingerprinting to different keys because the trailing clause describing retry position varies by definition, not because the numbers inside it weren't stripped. `fingerprintErrorMessage` now strips `"· attempt N/M"` and `"· dead-lettered after N attempts"` clauses before the digit-stripping pass, so the same fault clusters together regardless of where in the retry cycle it was caught. This is a normaliser fix, not a seed fix — the same shape of message will occur with real production errors once M5's real workers exist. 2026-08-11.
